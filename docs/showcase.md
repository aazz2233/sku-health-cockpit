# 如何展示这个项目（投递与面试）

> 目标：让招聘方在 **30 秒**内知道这是什么，**10 分钟**内能跑起来，**面试时**经得起追问。

---

## 零、先理解对方的判断顺序

```
HR 扫一眼 → README 首屏（30 秒）
技术面试官 → 点开仓库看结构、看 CI、看有没有测试（3 分钟）
真正跑的人 → 按 README 敲命令，跑不通就关掉（10 分钟）
面试环节 → 挑 2~3 个点往深了问（15 分钟）
```

所以优先级是：**README 摘要 > 能跑起来 > 视频 > 代码细节**。
很多人反过来，把 80% 时间花在代码上，然后在第一屏就丢了。

---

## 一、投递前的 7 步

### 第 1 步：把仓库门面收拾好（10 分钟）

在 GitHub 仓库页点右上角 ⚙️ **About**：

| 字段 | 填什么 |
| --- | --- |
| Description | `Multi-store SKU profit / inventory health / anomaly diagnosis cockpit (Python + MySQL + Streamlit + LLM)` |
| Website | 留空或在录完视频后填 B 站链接 |
| Topics | `python` `pandas` `mysql` `sqlalchemy` `data-engineering` `anomaly-detection` `ecommerce` `streamlit` `llm` |

顺带确认：
- 绿勾存在（CI 通过，README 顶部有 badge）
- 仓库是 Public
- 没有 `.env`、没有 API key（拿不准就搜一遍 `sk-`）

### 第 2 步：确认 README 首屏能自证（5 分钟）

打开仓库首页，**只看第一屏不滚动**，应该能回答：
这是什么 → 用了什么技术 → 有什么结果数字 → 长什么样（截图）。

本仓库的第一屏已经包含：30 秒摘要、4 个关键数字、4 张看板截图。
如果哪天改了实现，记得同步这里的数字——**首屏数字和代码对不上，是硬伤**。

### 第 3 步：录一段 3 分钟视频（1 小时）

工具：OBS（录屏）或 Windows 自带 `Win + G`；GIF 用 ScreenToGif。

逐句脚本见本文**第三节**。要点：
- 先 `up.ps1` 把环境跑起来，**录制前 10 分钟预热一遍**，避免现场卡在依赖安装
- 不要念代码，念"为什么这么做"
- 结尾必须说局限（比吹功能加分）

### 第 4 步：把视频放进 README（10 分钟）

最省事：上传 B 站（设"仅链接可见"），README 顶部加一行：

```markdown
🎬 [3 分钟演示](https://www.bilibili.com/video/BVxxxx)
```

备选：剪 15 秒 GIF 放 `docs/images/demo.gif`（仓库别传超过 10MB 的视频）。

### 第 5 步：写一页 PDF 项目说明（30 分钟）

投递时附件用。结构直接对着 JD 的三问：

```
1. 解决了什么问题（3 行）
2. 我做了什么（5 条，每条带技术关键词）
3. 怎么验证的（4 个数字：脏数据召回、对账偏差、异常召回、AI 成功率）
4. 已知局限（2 条，显示你知道边界）
```

### 第 6 步：投递话术（5 分钟）

BOSS 直聘/邮件正文控制在 5 行，别贴整篇 README：

> 您好，我做了个跨境电商 SKU 经营诊断的项目，和岗位描述里"SKU 数据处理、利润测算、AI Agent"几条直接对应：
> 3 个店铺 8 万条订单 → 清洗入库（脏数据 100% 拦截）→ 算利润与库存健康 → 10 条规则识别异常 → 大模型做归因（引用校验，不让模型编数字）→ 人工复核。
> 代码：https://github.com/aazz2233/sku-health-cockpit ，3 分钟演示：<链接>
> 想请教一下，你们现在内部工具最花时间的环节是哪一块？

最后那句是钩子——让对方开口，比你继续说更有用。

### 第 7 步：面试前 30 分钟准备（见第四节）

## 二、现场演示的最短路径

```powershell
cd D:\实习项目demo
. .\scripts\up.ps1            # 环境检查 → 数据 → 入库 → 指标 → 检测 → 日报 → 看板
```

浏览器打开 `http://localhost:8501`，按这个顺序讲：

1. **总览**：今天的 GMV/净利/异常数，一句"净利率 11.7%，但 207 条 P0/P1 异常需要处理"
2. **SKU 健康**：勾"只看亏损"，指一个 SKU 说"这个 30 天亏了 9 千，点进去看"
3. **SKU 下钻**：收入与净利背离 → 成本结构饼图 → "广告占 7%，FBA 占 8.7%，成本占 64%"
4. **人审队列**：点一条 AI 诊断，读"可能原因"和"引用指标"，当场点"通过"
5. **日报**：打开 `reports/daily_2024-08-29.md`，"这就是运营早上收到的东西"

**不要**演示从零 `generate`（要等 40 秒），数据已经在库里了。

## 四、高频追问与回答要点

| 问题 | 答题骨架 |
| --- | --- |
| 为什么不让大模型直接算利润？ | 财务数字不能幻觉；规则可复现、可审计、零成本。模型只做"为什么"，且必须引用算好的指标，引用错了程序会抓出来 |
| 数据哪来的？会不会违规？ | 全部由带 seed 的生成器产生，不碰真实数据；不抓需登录页面，采集器默认关闭 |
| 召回 93% 怎么算的？精确率为什么只有 4%？ | 生成数据时埋了 81 个已知异常作为 ground truth，按区间重叠匹配。精确率低是因为标注集只覆盖注入异常，真实数据里还有大量未标注的亏损周——我抽查过，那些是真实亏损 |
| 数据量到千万行怎么办？ | 现在是全量重算（8 万行 6 秒）；瓶颈在 mart 的全表扫，下一步是增量物化 + 分区，或把聚合下推到列存 |
| 为什么头程用移动加权而不是 FIFO？ | 没有逐批出库记录，硬做 FIFO 等于编数据；加权平均是当前数据下最诚实的做法，README 写明了这个取舍 |
| 规则和模型怎么分工？ | 一切可计算的交给规则；模型只做归因和建议；模型的每条结论必须挂证据，不确定就转人工 |
| 这套东西真上线还差什么？ | 权限、调度（现在 cron 触发）、监控告警、真实费率表接入、人审反馈回流到阈值调优 |

## 五、五个常见翻车点

1. **首屏数字与代码不一致** —— 改完实现忘了改 README，一眼假
2. **承诺"全自动"** —— 实际 199/200 都要人审，说全自动会被追问穿
3. **把 key 推到公开仓库** —— 检查 `git log -p | findstr sk-`，有就立刻换 key 并清历史
4. **现场从零跑** —— 依赖安装 + 数据生成要几分钟，评审会等得不耐烦，提前预热
5. **只讲技术不讲业务** —— 这个岗位要的是"懂业务 + 能用 AI 落地"，天平在业务侧
