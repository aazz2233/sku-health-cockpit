# AI 归因层（P4）

> 目标：把"检测到一个异常"变成"告诉你可能为什么、该做什么"，但**不让模型碰数字**。

---

## 一、为什么需要这一层

P3 的规则能回答"哪个 SKU 出问题了"，回答不了"为什么"。而运营真正要的是后者。
但直接让大模型看数据、算利润，会得到看起来很专业、实际算错的结论——财务数字不能幻觉。

所以这一层的分工是：

```
规则引擎   →  算出所有数字（可复现、可审计）
AI        →  只解释这些数字，不许自己算
人        →  拍板
```

---

## 二、三道防线（核心设计）

### 防线 1：指标白名单

模型收到的不是原始数据，而是**已经算好的 24 个指标**，每个都有 `metric_id`：

| 指标 | 含义 |
| --- | --- |
| `rev_30d` `gmv_30d` `net_profit_30d` | 收入与利润绝对值 |
| `net_margin_30d` `gross_margin_30d` `net_margin_prev_30d` | 利润率与环比 |
| `cogs_30d` `referral_fee_30d` `fba_fee_30d` `storage_fee_30d` | 成本拆项 |
| `ad_spend_30d` `tacos_30d` | 广告 |
| `refund_30d` `refund_rate_30d` `return_loss_30d` | 退款与货损 |
| `available_qty` `days_of_cover` `reorder_point` `stock_status` | 库存 |
| `category_net_margin_30d` `category_refund_rate_30d` | 类目基线（判断"是不是行业普遍现象"） |

模型**看不到**订单明细、也不知道成本公式，所以它没有"自己算"的材料。

### 防线 2：引用校验

模型输出的每个 `cited_metrics` 都会被程序逐条核对：

| 检查 | 失败处理 |
| --- | --- |
| `metric_id` 在白名单里？ | 记录错误 → 重试 |
| 引用的数值与白名单一致（容差 1%）？ | 记录错误 → 重试 |
| 数值型指标被写成字符串？ | 记录错误 → 重试 |
| 枚举型指标（如库存状态）字符串完全匹配？ | 记录错误 → 重试 |
| `supporting_metric_ids` 都真实存在？ | 记录错误 → 重试 |

**关键点**：不是"提示模型别编"（没用），而是"编了就抓得出来"。

### 防线 3：降级模板

重试 2 次仍不过校验 → 输出**模板化解释**，内容全部来自白名单数字：

```
规则 R6 触发；近30天净利率 26.4%；净收入 79,075 元；广告费占比 4.8%。
需要人工复核：自动归因未通过校验，先按指标异常程度排序。
```

宁可给一个朴素但正确的结论，也不给一个漂亮但可能是错的结论。

## 三、事件选择

不是所有事件都值得花 token：

1. 只要 **P0 / P1** 严重度
2. 按**近 7 天利润影响绝对值**排序（金额大的先看）
3. 同一 SKU-店-日 多规则命中 → 只保留影响最大的一个（避免同一件事说三遍）
4. 取前 200 条

---

## 四、调用层

| 项 | 选择 | 原因 |
| --- | --- | --- |
| 协议 | OpenAI 兼容 + 显式 `api_base` | 账号暴露的模型名不在 litellm 内置映射里 |
| 模型 | `deepseek-flash` | 归因不需要长链推理，flash 足够且便宜 |
| 关闭思考 | `extra_body={"thinking": {"type": "disabled"}}` | **否则推理过程吃光 token 预算，正文为空** |
| 输出上限 | 1200 tokens | 实际用 400 左右 |
| 重试 | 2 次，带校验错误回喂 | 让模型知道自己错在哪 |

**实测对比**（同一条事件）：

| 配置 | 正文 | 推理 token | 输出 token |
| --- | ---: | ---: | ---: |
| 默认（允许思考） | 0 | 1200 | 1200（截断） |
| 放大到 4096 | 1549 字 | 1345 | 1038 |
| **关闭思考** | 1068 字 | 0 | **403** |

## 五、人审闭环

诊断结果写入 `diagnosis` 表，人工决策写入 `review_feedback`：

| 字段 | 含义 |
| --- | --- |
| `decision` | `approve` / `edit` / `reject` |
| `note` | 为什么这么判 |
| `reviewer` | 谁判的 |

这张表是后续优化的燃料：哪些规则产出的诊断总被驳回、哪类归因从来没被采纳，
都可以从它反推。**没有反馈闭环的 AI 功能，三个季度后一定退化成噪声源。**

## 六、结果（200 条高优先级事件，实测）

| 指标 | 值 |
| --- | ---: |
| 尝试归因 | 200 |
| LLM 成功 | **200** |
| 降级为模板 | 0 |
| 引用校验失败率 | **0%**（一次都没触发重试） |
| 输入 token | 273,342 |
| 输出 token | 107,090 |
| 平均延迟 | 2.72 秒/条 |
| 总耗时 | 547 秒 |

**怎么读这组数字**：
- 引用校验 0 失败，说明"只给白名单指标 + 严格 JSON + 关闭思考"这套组合下，模型没有编数字的动机和空间
- 2.72 秒/条意味着 200 条只要 9 分钟，可以放进每日批处理
- 模型几乎总把 `need_human_review` 设为 true——提示词明确要求"无法判断就标人审"，它照做了。代价是自动化程度低，收益是不给没把握的结论

**数据生命周期**：`ingest --drop` 会重建整个 schema，`diagnosis` 表随之清空。
重建数据后必须重跑 `detect` 与 `diagnose`（`scripts/up.ps1 -Rebuild` 会提示这一点）。

**样例**（R6 断货风险）：

> SKU-0045 触发缺货风险预警，可售库存低于补货点，但当前盈利与退款指标正常，需核实库存与补货数据。
> 原因：可售库存低于补货点（置信度 0.75，引用 available_qty / reorder_point / stock_status）
> 建议：立即核实库存与在途补货，按补货点下单；风险：补货过量占用资金

引用值全部可回溯到 `mart_sku_daily` 的具体字段。

## 七、已知局限

| 局限 | 说明 |
| --- | --- |
| 单 SKU 视角 | 看不出"同一批货 5 个 SKU 同时出问题"这种关联异常 |
| 无竞品与市场数据 | 无法区分"我变差了"和"大盘变差了" |
| 归因是相关性不是因果 | 输出写的是"可能原因"，措辞上必须留余地 |
| 类目基线只有同店同月 | 样本小，基线本身有噪声 |

---

## 八、踩坑记录（都是"看起来能跑"的坑）

1. **provider 路由**：`deepseek/deepseek-chat` 在这类账号上不认，换成 openai 兼容协议 + `api_base` 才通。
2. **响应被 markdown 包裹**：即使设了 `response_format=json_object`，模型偶尔仍返回 ` ```json ... ``` `，导致 `json.loads` 在第一个字符就报"Expecting value"——**看起来像空响应，其实是格式问题**。
3. **推理模型吃光预算**：`max_tokens=1200` 全部用于 `reasoning_content`，`content` 为空、`finish_reason=length`。不关思考就会一直是"调用成功但没结果"。
4. **枚举值被当成数字**：模型引用 `stock_status` 时给出字符串，而 schema 只收 float → 校验失败。这不是模型的错，是校验规则太窄。
